Python bindings (neon_pde)¶

NeoN provides Python bindings that expose the core containers, executors, fields and DSL to Python. The distribution is named neon_pde on PyPI, but the import package is neon:

import neon
neon.initialize()
exec = neon.CPUExecutor()
v = neon.ScalarVector(exec, 10, 1.0)
neon.finalize()

The package supports CPython 3.9–3.13 and depends on NumPy.

Installing¶

CPU wheels from PyPI¶

Pre-built CPU wheels are published to PyPI for Linux (x86-64 and ARM64), Windows (AMD64) and macOS (Apple Silicon and Intel). These are the default wheels for most users and require no CUDA toolkit or GPU:

pip install neon_pde

CPU wheels are built with the serial and OpenMP (CPU) Kokkos back ends. MPI and the optional HPC dependencies (PETSc, ADIOS2, SUNDIALS) are disabled so the package installs without external HPC libraries.

GPU wheels from GitHub Releases¶

GPU wheels are not published to PyPI. They are large and carry a local version identifier, which PyPI rejects, so they are attached to the matching GitHub Release instead.

Four variants are built. Each CUDA and ROCm major needs its own wheel, because minor-version compatibility does not span majors and the vendor libraries are linked against the host’s sonames, which carry the major version:

All four are CPython 3.12 on Linux x86-64 (manylinux_2_34, glibc ≥ 2.34). Download from the release page, or install directly by URL:

pip install https://github.com/exasim-project/NeoN/releases/download/v0.1.0/neon_pde-0.1.0+cuda128-cp312-cp312-manylinux_2_34_x86_64.whl

Note

Kokkos rejects multiple GPU architectures in a single build (kokkos_arch errors with “Multiple GPU architectures given!”), so one wheel cannot carry both sm_80 and sm_90 cubins the way a pure-Ginkgo build can. The CUDA wheels compile sm_80 and embed PTX, so Hopper (sm_90) and newer cards run them by JIT-compiling at first kernel launch — correct, but with a one-off compile cost. Build from source to target sm_90 natively.

The vendor runtime libraries are excluded from the wheels rather than bundled. For CUDA that is libcuda.so.1 (it must match the installed driver) plus the math libraries Ginkgo links — cuBLAS, cuSPARSE, cuRAND, cuFFT — which together push the wheel to the edge of GitHub’s 2 GiB release asset limit. libcudart stays in the wheel: it is small, and keeping it matched to the build avoids a runtime version mismatch. For ROCm the entire userspace stack is excluded (rocBLAS alone ships multi-hundred-MB Tensile kernel archives). A CUDA wheel therefore needs a matching host CUDA toolkit and driver; a ROCm wheel needs a matching host ROCm, typically loaded with module load rocm.

Because GitHub-hosted runners have no GPU, GPU wheels are not runtime-tested in CI and must be validated on a machine with a compatible driver and GPU.

Building from source¶

Building the bindings compiles the NeoN C++ library through scikit-build-core, so it needs a C++20 compiler and CMake ≥ 3.22 (see Installation). From the repository root:

pip install .                # CPU build using the production preset

Build options are forwarded to CMake with --config-settings. To build a CUDA-enabled package matching the released wheels:

pip install . \
  --config-settings=cmake.define.NeoN_BUILD_PYTHON_BINDINGS=ON \
  --config-settings=cmake.define.Kokkos_ENABLE_CUDA=ON \
  --config-settings=cmake.define.Kokkos_ARCH_AMPERE80=ON \
  --config-settings=cmake.define.CMAKE_CUDA_ARCHITECTURES=80 \
  --config-settings=cmake.define.CMAKE_CUDA_STANDARD=20

Swap Kokkos_ARCH_AMPERE80/CMAKE_CUDA_ARCHITECTURES for Kokkos_ARCH_HOPPER90/90 to target sm_90 natively. The ROCm equivalent builds the whole project with ROCm’s clang++, the same way ci/lrz-gitlab/build-and-test.sh does:

pip install . \
  --config-settings=cmake.define.NeoN_BUILD_PYTHON_BINDINGS=ON \
  --config-settings=cmake.define.CMAKE_CXX_COMPILER=/opt/rocm/llvm/bin/clang++ \
  --config-settings=cmake.define.CMAKE_PREFIX_PATH=/opt/rocm \
  --config-settings=cmake.define.Kokkos_ENABLE_HIP=ON \
  --config-settings=cmake.define.Kokkos_ARCH_AMD_GFX90A=ON \
  --config-settings=cmake.define.CMAKE_HIP_ARCHITECTURES=gfx90a

For local development, an editable install rebuilds on import:

pip install -e .[dev]

Verifying an installation¶

The bindings expose the version and the compiled back-end feature flags. Use them to confirm which executors a wheel supports:

import neon
print(neon.__version__)      # e.g. 0.1.0 (or 0.1.0+cuda128 for a CUDA wheel)
print(neon.__has_serial__)   # serial executor available
print(neon.__has_cpu__)      # CPU (OpenMP) executor available
print(neon.__has_gpu__)      # GPU (CUDA/HIP) executor available

The repository ships an equivalent smoke test at ci/check_installed_wheel.py that CI runs against every repaired CPU wheel.

Running the binding tests¶

The Python test suite lives in test/bindings and is driven by pytest:

pip install .[test]
pytest test/bindings

Tests marked gpu are skipped automatically when no GPU executor is available.

Versioning and release workflow¶

The package version in pyproject.toml is the single source of truth. CMake reads it during configuration and it becomes neon.__version__.

Wheels are produced by the .github/workflows/python_wheels.yaml GitHub Actions workflow using cibuildwheel:

  • Stable releases are triggered by tags named v*.*.* (e.g. v0.1.0). CPU wheels are published to PyPI via Trusted Publishing, and CUDA wheels are attached to the GitHub Release for the tag.

  • Manual builds (workflow_dispatch) produce a development version with a .dev suffix. Dispatch with build_wheels, build_cpu and publish_repository=testpypi to rehearse a publish against TestPyPI without touching the production index.

  • The workflow does not run on ordinary branch pushes or pull requests.

For the full CI/CD description, including recovery paths for re-publishing already-built artifacts, see Continuous Integration.
