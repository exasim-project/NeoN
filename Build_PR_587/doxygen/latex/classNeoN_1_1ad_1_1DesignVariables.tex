\doxysubsection{Detailed Description}
\subsubsection*{template$<$typename Value\+Type, int NDeriv$>$\newline
class Neo\+N\+::ad\+::\+Design\+Variables$<$ Value\+Type, NDeriv $>$}
Registry mapping named design variables onto derivative slots. 

The registry mediates between two views of the same data\+:
\begin{DoxyItemize}
\item the user, who wants named, typed handles ({\ttfamily nu}, {\ttfamily source\+Strength});
\item the optimiser, which wants a flat, scaled vector of length n\+Alpha.
\end{DoxyItemize}

Declaration returns an {\itshape active} \doxylink{classNeoN_1_1Dual}{Dual} seeded in its own slot. From that point the value is usable anywhere the underlying arithmetic type is usable, so no AD-\/specific syntax appears in the equation the user writes.

Scope of this MWE\+: scalar and small-\/array design variables (model coefficients, operating conditions). Boundary-\/ and volume-\/field design variables need n\+\_\+alpha to exceed what forward mode can carry and are therefore deferred to the adjoint work; the declaration API is sketched at the bottom of this header so the intended shape is on record.

Mesh coordinates are explicitly {\itshape out} of scope\+: geometric quantities remain plain \doxylink{namespaceNeoN_a93c8d00d3aa9fc6f9271c4c0b4f0da97}{Neo\+N\+::scalar} so that any attempt to differentiate through mesh metrics is a compile error rather than a silently wrong sensitivity.

Report design variables with exactly zero sensitivity. 

\doxylink{classA}{A} declared variable with no path to the functional yields an identically zero gradient. This is almost always a user error -\/ a coefficient copied into a passive Value\+Type somewhere along the chain, or a typo in the case setup -\/ and returning zeros silently is the worst possible outcome, since the optimiser will simply never move that variable. Callers should treat a non-\/empty result as a warning.
